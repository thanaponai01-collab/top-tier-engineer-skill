Snapshot: [`4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536`](https://github.com/cursor/plugins/tree/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack). These are source instructions, not evidence that an agent consistently obeys them or that the workflow outperforms another one. No pstack behavior eval was executed in this research.

## What the verification mechanism does

- **Make the application controllable.** `create-verification-skill` inspects the repo for the real user surface, startup, an existing harness, observation methods, and instance isolation. It generates a project-local verification skill with exact Launch, Doctor, Drive, Evidence, and Cleanup instructions. It prefers existing harnesses before introducing generic browser, PTY, or HTTP recipes. [Source](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/create-verification-skill/SKILL.md).
- **Keep a user-facing feature map.** Generated feature files enumerate entry points, subfeatures, real driving steps, observable end states, and gotchas. Its example explicitly reopens saved data from a second user-facing view; a save toast alone does not count. Generation targets roughly 3–5 features but executes only one feature end to end before delivery. [Generator](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/create-verification-skill/SKILL.md), [example](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/create-verification-skill/references/feature-map-example/create-note.md).
- **Preserve evidence and clean failed attempts.** Proof records the action and result, including side effects. Internal setters and test-only endpoints do not replace a real path. Mocks are restricted to existing production boundaries. Cleanup targets owned instances, preserves evidence, and runs after failed iterations too. [Source](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/create-verification-skill/SKILL.md).
- **Maintain the harness and map separately from the product.** Maintenance uses parallel read-only source readers per feature, then a coordinator serially drives a shared live instance (fresh isolated sessions for short-lived CLIs). Every feature receives source and live coverage. Product failures are reported, not fixed by changing their description. Doctor checks recur after surprising results, with state reset when process health cannot reveal a wedged UI. Outcomes are clean, changed, or blocked. [Source](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/maintain-verification-skill/SKILL.md).
- **Prove the safety assumption behind a change.** `blast-radius` follows indirect consumers and boundary formats beyond symbol searches, identifies the one or two decisive safety facts, and runs actual code to test them. It reports how far the evidence reached, from source citation through live reproduction. [Source](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/blast-radius/SKILL.md).
- **Bind shipping verdicts to the patch.** Shipping requires a fresh verifier per PR driving the matching real surface against parent and head. It records head/base SHA and stable patch ID, rechecks validity after rebases, and lands only the contiguous verified stack. Changed patches usually require renewed verification. It has a more complex exception for changes limited to tests/docs/lint configuration, comparing repeated builds and classifying output noise. [Source](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/poteto-mode/playbooks/shipping.md).
- **Make checks capable of rejecting real mistakes.** `correct` prioritizes architecture, types, then lint/test enforcement; a new check must fail on an actual past mistake. `principle-prove-it-works` prefers retained deterministic scripts over a one-time visual judgment. [Correct](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/correct/SKILL.md), [proof principle](https://github.com/cursor/plugins/blob/4e5b1cf2ccb0ea3716f08c8ee0a5856b5ab93536/pstack/skills/principle-prove-it-works/SKILL.md).

## Strengths worth borrowing

The most concrete contribution is a reusable app-driving recipe. It reduces repeated discovery and gives agents exact readiness checks, selectors, artifact locations, and teardown. This is more actionable than merely telling an agent to run the feature. The map also makes alternate entry points visible. Evidence surviving cleanup, rechecking health after a failed drive, and distinguishing doc drift from product regression are practical safeguards. These conclusions are inferences from the generator and maintenance mechanisms above, not measured results.

Patch-bound evidence is another strong idea: a successful run belongs to a particular artifact, not forever to a branch name. The shipping source makes this explicit rather than equating CI status with observed behavior. Its full stack/forge/build-noise machinery is unnecessary for a small general-purpose correctness skill; the small transferable rule is to record the tested revision and invalidate affected evidence after changes.

## Limits and opportunities

1. **A feature map is not a requirement oracle.** The same repo can supply both the behavior and the generated expected result. Maintenance distinguishes regression from drift, but its text does not prescribe an external requirement authority for that decision. An implementation bug can become the documented expectation. Improvement: derive expected outcomes from the task/spec or an explicit existing contract; do not silently redefine them to match observed behavior. This is an inference about the generator and maintenance instructions, not a demonstrated defect.
2. **Feature coverage is coarser than scenario coverage.** Maintenance says every feature at least once and explicitly avoids covering every bullet; generation executes one mapped feature. This does not establish coverage of each entry point, failure, retry, restart, authorization boundary, or concurrency case. Improvement: select changed and risk-relevant scenarios, record uncovered ones honestly, and reserve a full map audit for maintenance. Source: generator and maintenance above.
3. **Independent agents reduce author bias; they do not prove correctness.** Shipping defines a safe verdict using a verifier who did not write the code. Review diversification can help find omissions, but agents can share faulty assumptions, weak oracles, or the same mocked boundary. Improvement: require a runnable observation and a falsifiable assertion for material claims; a reviewer verdict supplies judgment, not a replacement for evidence. Source: shipping above; limitation is inference.
4. **No universal failing-control requirement in live verification.** `correct` requires new enforcement checks to reject a past mistake, but generation/maintenance do not universally require proving each verification assertion can fail. Improvement: for a changed claim, replay the old bug or use a small deliberate bad input/state; confirm the check rejects it, then confirm the real fixed path passes. Do this where meaningful, without universal mutation-testing infrastructure. Source: correct, generator, maintenance above.
5. **Patch sameness does not establish environment sameness.** Shipping handles code revision changes, but a matching patch can still behave differently with configuration, data, dependencies, or external services. Improvement: record only the environment facts material to the claim (build identity, relevant flag, real/mocked boundary), and rerun if those facts change. Source: shipping above; inference.

## Smallest useful adoption

Keep the existing correctness skill as the gate. Add a short rule: each material outcome needs an expected result from a named contract, a real user entry path, an observable assertion, the tested revision/environment, and an evidence location. Require one relevant bad case or before-fix replay when practical. After a change, rerun affected claims. Report pass, fail, or unverified per claim; blocked or unreachable is a coverage gap, never a successful behavioral check.

For repos repeatedly difficult to drive, document a small project-local Launch / Doctor / Drive / Evidence / Cleanup recipe using their existing harness. Add a feature index only when repeated verification justifies maintaining it. Do not transplant pstack's multi-model roster, shipping stack machinery, or entire feature-map maintenance workflow into every task.

## Local comparison and reproduction evidence

The coordinating agent inspected the local [`verify.py`](../skills/verify-loop/scripts/verify.py), the correctness and wiring skills, and the existing drive implementation. Its findings: verification accepts nonempty prose proof entries; strict checks omit orphan coverage and skipped-test policy; check hashes bind discovered tests and commands but omit smoke helpers/fixtures; a tree signature uses file size and modification time; status does not retain whether the preceding run required strict verification. Drive already has content-bound input/oracle contracts and external-CI independence, so extend that existing mechanism rather than invent a second receipt system. These are coordinator-supplied findings, not additional pstack claims.

The coordinator also ran two isolated temporary-directory reproductions with `VERIFY.md` and a check command `python -c "pass"`:

- With arbitrary fail-proof prose, `run --strict` returned 0 and subsequent `status` was green. This proves a no-op command plus prose can satisfy that gate; it does not prove zero test discovery, because no test runner was invoked.
- Without the fail-proof prose, `run --strict` returned 1 with one unproven item, but immediately following `status` returned 0 and green. This proves strict-run/status verdict disagreement.

Priority: first make strict verdict and subsequent status agree; second adopt pstack's instance doctor, real user path, and evidence persistence; third replace prose-only negative proofs with executable rejection receipts and bind relevant inputs by content, reusing drive. No skills or product implementation were edited in this research.
