# Optional competing designs

Use this only when the shape is genuinely uncertain and a wrong choice has material cost: ownership,
concurrency, an expensive migration, or a public/stored contract. A settled, routine edit stays with
its current owner; do not add a candidate round, workers, or a review matrix.

1. Write the hard requirements and rank the decision criteria before drafting options. Label unknown
   values and assumptions; ask the owner only for facts that change which option meets the bar.
2. Start with the simplest viable design, reusing existing owners. Add at most one structurally
   different candidate that answers a real criterion the first cannot meet. Keep sketches at the
   boundary/contract level, not competing codebases.
3. Isolate the sketches: each designer sees the same requirements and criteria, not another sketch.
   Use up to two design contributors and one coordinator, one round only, within an explicit time and
   spend cap. No recursive critiques or full option matrix.
4. If the host cannot provide isolated contributors, compare the two structural shapes in the current
   session and say they are same-model sketches. Never claim worker dispatch or model diversity that
   did not happen. If available seats, time or cost are unclear, use the current session only.
5. Select a complete candidate against the criteria and explain its tradeoff. Do not blend options by
   default. If a synthesis keeps parts of both, replay every hard criterion against that combined
   design and check its contracts; otherwise choose one base and name what it gives up.

Stop when the criteria decide the choice. Hand the selected move to the existing deep-dive/build flow;
this procedure does not authorize implementation or release.
